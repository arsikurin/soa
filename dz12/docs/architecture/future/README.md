# Целевая архитектура маркетплейса

Модель первого задания: разделение на пять сервисов, API Gateway и gRPC.
Она описывает весь проект, включая ещё не реализованные Payments, Notifications и обмен событиями. Запускаемое приложение и актуальная C4-модель описаны в [README проекта](../../../README.md).

Предположения ниже сохранены вместе с исходной моделью. Во втором задании Gateway, Users, Catalog и Orders уже работают отдельно; заказ и складские остатки согласуются через 2PC между базами Orders и Catalog. Промокоды принадлежат Orders.

## 3. Предположения и границы кейса

- Один пользователь может иметь роли покупателя и продавца.
- Один заказ содержит товары одного продавца; покупки у нескольких продавцов
  оформляются отдельными заказами.
- Одна валюта — RUB; денежные суммы хранятся целыми числами в копейках.
- Стоимость заказа равна сумме `количество × зафиксированная цена` по позициям.
  Скидки, платная доставка, комиссии и выплаты продавцам не входят в модель.
- Каталог хранит доступность предложения (`active` / `hidden`). Складской учет
  и резервирование конечных остатков не проектируются. Для физических товаров
  с ограниченным запасом перед оплатой потребуется отдельный протокол резервирования.
- Уведомления отправляются по email. SMS, push, логистика, возвраты и споры
  не входят в модель.

## 4. Домены, ответственность и владение данными

| Домен | Ответственность | Сервис-владелец | Собственные данные |
|---|---|---|---|
| Пользователи | Регистрация, аутентификация, роли покупателя/продавца, профиль и настройки | **Users Service** | Users DB: аккаунты, хеши паролей, роли, email, любимые категории, согласие на уведомления |
| Товарный каталог | Публикация и изменение своих товаров продавцом, категории, цены, доступность предложения | **Catalog Service** | Catalog DB: карточки, `seller_id`, категории, актуальные цены, `active` / `hidden` |
| Персональная лента | Ранжирование доступных товаров по интересам пользователя | **Catalog Service** | Отдельной БД нет; используются собственные товары и предпочтения, полученные через Users API |
| Заказы | Фиксация состава покупки и цен, жизненный цикл заказа, проверка доступа к заказу | **Orders Service** | Orders DB: заказы, покупатель/продавец, неизменяемые снимки позиций и цен, итог, статус, ссылка оплаты, версия заказа, последовательность и архив событий статуса, outbox/inbox |
| Платежи | Расчет суммы платежа по снимку заказа, создание попытки оплаты, учет результата и сверка с провайдером | **Payments Service** | Payments DB: сумма и валюта платежа, попытки, ключи идемпотентности, идентификаторы провайдера, статусы, журнал операций, outbox/inbox |
| Уведомления | Доставка сообщений о статусах заказа, повторы и учет доставки | **Notifications Service** | Notifications DB: задания, шаблоны, история попыток и доставки, обработанные `event_id` |

Web SPA содержит витрину и кабинет продавца, вызывает API через Gateway
и переводит покупателя на страницу оплаты. Для SPA выбран React/TypeScript,
для сервисов — Go, для БД — PostgreSQL, для сообщений — RabbitMQ.

API Gateway на Envoy принимает HTTPS/JSON-запросы SPA, преобразует их в gRPC-вызовы
Users, Catalog или Orders и возвращает ответ в JSON. Фильтр
[`grpc_json_transcoder`](https://www.envoyproxy.io/docs/envoy/latest/configuration/http/http_filters/grpc_json_transcoder_filter)
использует дескрипторы Protobuf и HTTP-маршруты из аннотаций `google.api.http`.
Gateway завершает TLS-соединение клиента, ограничивает частоту запросов,
число активных вызовов и ведет журнал обращений. Он хранит конфигурацию маршрутов,
сертификатов, лимитов и дескрипторы API; бизнес-данных и отдельной БД у него нет.

SPA использует один адрес API. Gateway обращается к сервисам по gRPC через HTTP/2
с mTLS; межсервисные вызовы идут напрямую по тому же протоколу.

gRPC-обработчик сервиса вызывает метод приложения, реализующий бизнес-операцию. Envoy преобразует
публичный REST-запрос в вызов этого обработчика; отдельный HTTP-обработчик
для той же операции не нужен. HTTP-маршруты и JSON-ответы проверяются через Gateway.

### Правила владения

1. Доступ к каждой БД есть только у сервиса-владельца. Общих таблиц
   и межсервисных SQL-запросов нет. У каждой БД свои учетные данные,
   миграции и резервные копии.
2. Чужие сущности доступны только через API или сообщения. `user_id`, `seller_id`
   и `product_id` — логические ссылки; внешних ключей между сервисами нет.
3. Снимок цены и названия в заказе принадлежит Orders. Изменение каталога не меняет
   уже оформленный заказ.
4. Users хранит профиль и предпочтения. Catalog запрашивает предпочтения через API
   при построении ленты. Notifications получает адрес и согласие через
   Users API; задание доставки может содержать снимок адреса на момент отправки.
5. Payments хранит состояние платежа, Orders — состояние заказа
   и копию результата оплаты. Карточные реквизиты вводятся
   на стороне провайдера и не хранятся в БД маркетплейса.
6. RabbitMQ доставляет события. Схему события определяет отправитель;
   очередь и обработчик принадлежат потребителю.

### Почему каталог и лента вместе

Лента строится из тех же карточек, цен и категорий, которыми владеет Catalog.
Отдельному Feed потребовался бы вызов Catalog либо собственная копия каталога
с синхронизацией изменений. Для сортировки по категориям такая сложность избыточна.
Поэтому Catalog отвечает и за управление товарами, и за выдачу.
Отдельный Feed стоит рассмотреть при появлении ML, поведенческих событий
или необходимости независимо масштабировать ранжирование.

Остальные границы разделяют разные правила и жизненные циклы: Users управляет
аккаунтами и ролями, Orders — покупкой, Payments — взаимодействием с платежным провайдером,
Notifications — доставкой сообщений. Ошибка email-провайдера не должна блокировать заказ.

## 5. Персонализация

Пользователь явно выбирает любимые категории в профиле. Для авторизованного
пользователя Catalog запрашивает их у Users и сортирует доступные товары:

1. Сначала товары из любимых категорий.
2. Внутри каждой группы — более новые карточки первыми.
3. При одинаковой дате — по `product_id`, чтобы порядок был определенным.

Для гостя, пустого списка интересов или недоступного Users API Catalog
возвращает общую ленту по новизне. Выдача продолжает работать без персонализации.

## 6. Взаимодействия

Для внутренних синхронных API выбран gRPC с Protobuf: один запрос — один ответ
(unary RPC), транспорт — HTTP/2 с mTLS. Асинхронные события доставляет RabbitMQ.

| Инициатор → получатель | Данные / действие | Способ |
|---|---|---|
| Покупатель / продавец → Web SPA | Работа с витриной, заказами и кабинетом | Через браузер, HTTPS |
| Web SPA → API Gateway | Запросы к API маркетплейса | Синхронно, HTTPS/JSON |
| API Gateway → Users | Вход, профиль, любимые категории, настройки | Синхронно, gRPC/Protobuf + mTLS |
| API Gateway → Catalog | Получение ленты; управление собственными товарами | Синхронно, gRPC/Protobuf + mTLS |
| API Gateway → Orders | Создание заказа, чтение статуса и ссылки оплаты, изменение статуса продавцом | Синхронно, gRPC/Protobuf + mTLS |
| Catalog → Users | Любимые категории текущего пользователя | Синхронно, gRPC/Protobuf + mTLS; при сбое общая лента |
| Orders → Catalog | Снимок выбранных товаров, продавца и цен из каталога | Синхронно, gRPC/Protobuf + mTLS |
| Orders → Payments | Создание оплаты по сохраненному снимку заказа, получение ссылки оплаты | Синхронно, gRPC/Protobuf + mTLS, metadata `idempotency-key: order_id` |
| Payments → платежный провайдер | Создание платежа; запрос его состояния при сверке | Синхронно, HTTPS/JSON |
| Web SPA → платежный провайдер | Переход на полученную страницу оплаты | HTTPS, переход браузера |
| Платежный провайдер → Payments | Результат оплаты | Асинхронный callback; доставка HTTPS webhook |
| Payments → Orders | `PaymentSucceeded` / `PaymentFailed` | Асинхронно, AMQP 0-9-1 через RabbitMQ, очередь `orders.payment-results` |
| Orders → Notifications | `OrderStatusChanged` | Асинхронно, AMQP 0-9-1 через RabbitMQ, очередь `notifications.order-status` |
| Notifications → Users | Email и разрешение на уведомления | Синхронно, gRPC/Protobuf + mTLS, внутри фонового задания |
| Notifications → email-провайдер | Отправка письма | Синхронно, HTTPS API, внутри фонового задания |
| Каждый бизнес-сервис → собственная БД | Чтение / запись только собственных данных | Синхронно, PostgreSQL wire protocol / TCP |

Для gRPC-вызовов задается deadline — предельное время ожидания ответа;
вложенные вызовы учитывают оставшееся время. Для внешних HTTPS-запросов задаются
тайм-ауты. Превышение deadline не означает, что сервер не успел сохранить данные:
повтор запроса на изменение использует тот же ключ идемпотентности.
Orders передает `order_id` в Payments через metadata `idempotency-key`.

### Контракты API

Контракты бизнес-API хранятся в `.proto`; за каждый отвечает сервис-владелец.
Версия входит в имя пакета, например `marketplace.orders.v1`. Из одной ревизии
контракта собираются Go-интерфейсы серверов, клиенты и дескрипторы для Envoy.
HTTP-маршруты задаются в `google.api.http`; версии генераторов и зависимостей фиксируются.

Для CI предусмотрены `buf lint` и `buf breaking` с категорией
[`FILE`](https://buf.build/docs/breaking/). Она проверяет совместимость схемы
для сгенерированного кода, бинарного Protobuf и JSON. База сравнения — сохраненные
контракты поддерживаемых релизов. Коды ошибок и смысл полей проверяют контрактными
тестами gRPC, а HTTP-маршруты и JSON-ответы — тестами через Envoy. Buf этих изменений
поведения не проверяет.

В пределах `v1` сохраняется совместимость с действующими клиентами. Устаревшие поля
и методы помечаются `deprecated` и сохраняются до снятия версии с поддержки.
Несовместимые изменения выходят в `v2`; сервер обслуживает обе версии до перехода
клиентов. В новой версии номера и имена удаленных полей резервируются и не
используются повторно. Для JSON API версиям соответствуют маршруты `/api/v1/...`
и `/api/v2/...`.

### Аутентификация сервисов и права доступа

Вызовы бизнес-API используют [mTLS](https://grpc.io/docs/guides/auth/): Gateway
и сервисы предъявляют сертификаты внутреннего центра сертификации. При соединении
проверяются цепочка доверия, срок действия и идентификатор сервиса в SAN сертификата;
клиент сверяет его с ожидаемым получателем. У каждого сервиса свой идентификатор
и ключи; имя вызывающего сервиса из заголовков запроса не используется для проверки прав.

Серверный gRPC interceptor проверяет, разрешен ли этому идентификатору конкретный
метод. Вызов, для которого нет разрешения, отклоняется с `PERMISSION_DENIED`.

| Вызывающий сервис | Разрешенные операции |
|---|---|
| Gateway → Users | Регистрация, вход и операции с профилем текущего пользователя |
| Gateway → Catalog | Чтение ленты и управление товарами текущего продавца |
| Gateway → Orders | Создание и чтение своих заказов; изменение статуса заказа его продавцом |
| Catalog → Users | Чтение любимых категорий текущего пользователя |
| Orders → Catalog | Чтение снимка выбранных товаров и цен |
| Orders → Payments | Создание оплаты и получение ее ссылки по сохраненному заказу |
| Notifications → Users | Чтение email и согласия получателя уведомления |

В методах, доступных через Gateway, сервис дополнительно проверяет токен Users,
роль и владельца ресурса. Gateway передает токен в gRPC metadata `authorization`.
Catalog передает его в Users при запросе любимых категорий; Users проверяет, что
запрошены предпочтения владельца токена. Подпись проверяется локально по публичному
ключу, также проверяются срок действия, издатель и аудитория. Для регистрации,
входа и общей ленты токен пользователя не нужен. Вызовы Orders к Catalog и Payments
используют разрешения сервиса; права пользователя Orders проверяет до создания
заказа. Notifications обращается в Users по разрешению сервиса за контактами
получателя из задания.

Внутренние Payments API недоступны из SPA и не публикуются через Gateway.
Для webhook выделен отдельный публичный HTTPS endpoint Payments с проверкой
подписи провайдера. Браузер и внешние провайдеры не используют внутренние сертификаты.

Сертификаты и закрытые ключи поступают через секреты развертывания. Сертификаты
обновляются до истечения срока действия с перезагрузкой TLS-конфигурации.
При смене центра сертификации сначала распространяется набор доверия со старым
и новым CA, затем заменяются сертификаты и закрываются старые соединения;
после перехода всех сервисов старый CA удаляется. Ключи подписи токенов Users
имеют отдельную ротацию.

### Ограничение нагрузки и повторы

Фильтр rate limit в Envoy ограничивает частоту запросов клиента; при превышении
возвращает HTTP 429. [Circuit breakers Envoy](https://www.envoyproxy.io/docs/envoy/latest/intro/arch_overview/upstream/circuit_breaking)
ограничивают число активных RPC к каждому сервису и очередь ожидания подключения.
При достижении этих лимитов Gateway возвращает HTTP 503.

Каждый сервис ограничивает число одновременно выполняемых RPC и при перегрузке
отвечает `RESOURCE_EXHAUSTED`. Клиенты внутри сервисов отдельно ограничивают
активные вызовы к каждой зависимости; при достижении лимита отклоняют новый вызов.
Эти ограничения нужны и для прямых межсервисных запросов, которые обходят Gateway.
Число активных вызовов, размеры очередей и длительность deadline задаются
в конфигурации; их значения выбираются по результатам нагрузочных проверок.

| Вызов | Кто и когда повторяет |
|---|---|
| Gateway → Users, Catalog, Orders | Envoy не повторяет запрос: возвращает ответ или ошибку в SPA |
| Catalog → Users | Catalog не повторяет запрос; при недоступности Users возвращает общую ленту |
| Orders → Catalog | Orders допускает один повтор чтения при `UNAVAILABLE`, если остается время до deadline |
| Orders → Payments | Orders допускает один повтор при `UNAVAILABLE` с теми же данными и `idempotency-key: order_id` |
| Payments → платежный провайдер | Payments сохраняет попытку до обращения к провайдеру; после временной ошибки фоновая сверка запрашивает состояние или повторяет создание с тем же ключом |
| Notifications → Users / email-провайдер | Повтор назначает обработчик задания с задержкой; клиент API внутри одной попытки задания повторов не делает |

Orders делает не более двух попыток на каждый вызов Catalog или Payments.
Повтор выполняет gRPC-клиент; дополнительного цикла повторов в обработчике нет.
Пауза со случайным разбросом и обе попытки входят в общий deadline. В синхронном RPC
ошибки входных данных, прав доступа, `RESOURCE_EXHAUSTED` и истекший deadline
автоматически не повторяются. Неизвестный результат создания оплаты разбирает
фоновая сверка. Число попыток и повторяемые коды задаются в
[политике повторов gRPC](https://grpc.io/docs/guides/retry/).

Обработчики RabbitMQ ограничивают число параллельных заданий и неподтвержденных
сообщений (`prefetch`). Повторы выполняются с растущей задержкой и случайным разбросом,
а не немедленным возвратом сообщения в ту же очередь. Предел попыток задается
для каждого обработчика; после него сообщение отправляется в DLQ.

### Сценарий оформления и оплаты

1. SPA передает через Gateway в Orders идентификаторы товаров, количество
   и ключ запроса.
   Orders запрашивает Catalog, проверяет доступность и одного продавца, фиксирует
   снимок позиций и итог в заказе `pending_payment`. В той же транзакции записывает
   первое `OrderStatusChanged` с `status_sequence = 1`. Ценам из браузера не доверяет.
2. Orders вызывает Payments с `order_id`, снимком позиций и валютой. Payments
   вычисляет сумму в копейках, сверяет ее с итогом заказа и сохраняет попытку.
   Ключ `order_id` предотвращает создание второй оплаты при повторном вызове.
3. Payments создает платеж у провайдера с тем же стабильным ключом. Возвращает
   URL страницы оплаты; Orders сохраняет URL, SPA получает его из Orders API
   через Gateway.
4. Покупатель оплачивает на странице провайдера. Redirect обратно в SPA не служит
   доказательством оплаты. Payments проверяет подписанный webhook, сверяет
   идентификатор, сумму и валюту, фиксирует результат и событие в одной транзакции.
5. Orders получает `PaymentSucceeded` и переводит заказ в `paid`; при окончательном
   `PaymentFailed` — в `payment_failed`. Статус заказа и `OrderStatusChanged`
   записываются в одной транзакции. Продавец затем может перевести оплаченный заказ
   в `processing` и `completed` через Orders API; эти переходы также порождают событие.
6. Notifications обрабатывает `OrderStatusChanged`, получает контакт и согласие,
   отправляет письмо и записывает результат доставки. Ошибка отправки не откатывает заказ.

### Согласованность и отказы

- **Транзакции:** каждый сервис фиксирует изменения в своей БД;
  состояния разных сервисов согласуются через сообщения (eventual consistency).
- **Сбой при создании оплаты:** заказ остается `pending_payment`.
  Повторный вызов с тем же ключом возвращает тот же заказ/платеж. Фоновая сверка
  восстанавливает незавершенное создание оплаты после сбоя процесса.
- **Тайм-аут провайдера:** платеж
  остается `pending`; Payments повторяет идемпотентный запрос или запрашивает
  состояние. `PaymentFailed` публикуется только после подтвержденного окончательного
  отказа или истечения срока оплаты у провайдера. Переход из `paid` обратно запрещен.
- **Доставка сообщений — at least once:** Orders и Payments используют
  transactional outbox (запись состояния и события в своей БД одной транзакцией).
  Фоновый процесс публикации ждет подтверждения RabbitMQ. Потребитель подтверждает сообщение
  после фиксации локального результата, дубликаты отсекает по `event_id` в своей БД.
- **Порядок:** сообщения содержат `event_id`, `aggregate_id`, `aggregate_version`,
  `occurred_at` и версию схемы. Обработчики проверяют допустимость переходов и версию
  агрегата. У `OrderStatusChanged` дополнительно есть непрерывный `status_sequence`
  для каждого заказа: 1 при создании, затем +1 на каждый переход статуса. Сохранение
  ссылки оплаты не меняет этот счетчик. Notifications сохраняет задания и отправляет
  их последовательно по `status_sequence`; дубликаты уже обработанных номеров пропускает.
  При пробеле сохраняет позднее событие и ожидает недостающее, не удерживая его в
  неподтвержденной доставке RabbitMQ. Если пробел не закрывается после повторов,
  система контроля зависших заданий сообщает оператору: он повторно публикует нужное событие
  из DLQ или архива Orders с исходными `event_id` и `status_sequence`. Подтверждение
  брокера не удаляет историю: опубликованные события outbox сохраняются в архиве
  Orders для восстановления пропусков. При этом email-провайдер может доставить
  письма в почтовый ящик в другом порядке.
- **Недоступность брокера:** события сохраняются в outbox и публикуются позже;
  статус заказа может временно отставать от оплаты. Нужно отслеживать время ожидания
  событий в outbox и сверять зависшие платежи с провайдером.
- **Ошибка потребителя/email:** ограниченные повторы с увеличивающейся задержкой.
  После исчерпания попыток сообщение отправляется в очередь ошибок (DLQ),
  оператор получает оповещение. При неизвестном результате отправки email возможен дубль письма, если
  провайдер не поддерживает идемпотентность; повтор не должен менять состояние заказа.
- **Недоступность Catalog при оформлении:** заказ не создается по данным браузера;
  клиент получает временную ошибку и может безопасно повторить запрос. Уже созданный
  заказ использует свой снимок и не зависит от дальнейших изменений карточки.

## 7. Трассировка

Envoy и сервисы создают spans OpenTelemetry — записи о времени выполнения
операций и их результате. Трасса запроса связывает обращение к Gateway, обработку
в Orders и вызовы Catalog или Payments. По ней можно найти вызов, на котором
оформление заказа замедлилось или завершилось ошибкой.

Контекст трассы передается в заголовках HTTP, metadata gRPC и заголовках сообщений
RabbitMQ (`traceparent`, `tracestate`). Orders и Payments сохраняют контекст вместе
с событием в outbox, чтобы фоновый издатель мог передать его после перезапуска.
Обработчик сообщения создает span со ссылкой (span link) на этот контекст;
каждая повторная доставка получает отдельный span.

Webhook провайдера начинает новую трассу. Payments связывает ее с попыткой оплаты
по `payment_id` и `order_id`: наличие контекста трассы у внешнего провайдера
не предполагается. В журналах сервисы записывают `trace_id`, а для событий —
также `event_id`. Токены, email, реквизиты и полные тела запросов в трассы не попадают.

Envoy и сервисы отправляют spans в OpenTelemetry Collector по OTLP/gRPC с TLS.
Collector объединяет их в пакеты и отправляет в Jaeger по тому же протоколу.
Jaeger хранит трассы и предоставляет интерфейс поиска. Он работает одним процессом
со [встроенным Badger](https://www.jaegertracing.io/docs/2.21/storage/badger/)
на постоянном диске. Collector хранит конфигурацию и ограниченный буфер отправки в памяти.

Экспорт выполняется в фоне. При недоступности Collector или Jaeger запросы
маркетплейса продолжают работать. Очереди экспорта ограничены; после их заполнения
или истечения срока повторов часть spans теряется.
Доля отбираемых трасс и срок хранения задаются в конфигурации.

## 8. Варианты архитектуры

| Вариант | Разбиение | Плюсы | Минусы |
|---|---|---|---|
| **A. Модульный монолит** | Одно backend-приложение, шесть модулей, одна PostgreSQL БД; web-клиент отдельно | Один релиз и процесс; простая локальная отладка; локальные транзакции между заказом и внутренним учетом платежа; меньше затрат на инфраструктуру | Каталог и платежи масштабируются вместе; ошибка процесса затрагивает все модули; общий релиз; без дисциплины модульные границы размываются. Внешняя оплата все равно не входит в транзакцию БД |
| **B. Пять бизнес-сервисов и API Gateway — выбран** | Users, Catalog + Feed, Orders, Payments, Notifications; пять отдельных БД; Gateway для запросов SPA; gRPC внутри, HTTPS снаружи; сообщения через RabbitMQ; трассы через Collector в Jaeger | Владение данными явно разделено; чтение каталога можно масштабировать независимо; сбой уведомлений изолирован от оформления | Пять приложений и БД сложнее эксплуатировать; нужно обслуживать Gateway, Collector и Jaeger; заказ и платеж согласуются асинхронно; нужны outbox, дедупликация и контрактные проверки |

В варианте A модули вызывают друг друга внутри одного процесса и могут использовать
общую транзакцию. Единственная БД принадлежит этому backend-приложению.
В варианте B сервисы развертываются отдельно, обращаются друг к другу по сети
и согласуют изменения между своими БД.

### Решение: вариант B

Выбран вариант B: каталог можно масштабировать отдельно, платежную интеграцию —
обновлять без выпуска остальных сервисов, а сбой отправки писем не блокирует заказ.
У сервисов раздельные данные и правила: профиль пользователя, товары,
состояние заказа, учет платежа и доставка уведомлений. Лента остается в Catalog,
поскольку ее алгоритму достаточно карточек и любимых категорий.

Это усложняет эксплуатацию: нужны Gateway, пять БД, доставка событий, обработка дублей
и контроль сбоев. Collector и Jaeger требуют памяти, диска и настройки хранения трасс.
Общей транзакции между заказом и платежом нет.
Для небольшого MVP без требований к независимому масштабированию и изоляции
сбоев модульный монолит мог бы обойтись дешевле.
